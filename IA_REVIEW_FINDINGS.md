## Slice: canonical (NEEDS_FIXES)

### [data-loss] ed_people_canonical() and ed_sors_sor_record(), `out[row.entry_dn] = {...}` (slice not yet assembled into /Users/paulalbert/worktrees/reciterdb-ia/update/buildIdentityAuthority.py); consumed by plan_deletions() at buildIdentityAuthority.py:222

**Problem.** Switching the key from the SPL-reconstructed dn to row.entry_dn is right, but nothing migrates the existing rows. `_person_canonical.dn` and `_person_sor_record.dn` are populated today by `eval dn = "uid=" . uid . ",ou=people,dc=weill,dc=cornell,dc=edu"` (Splunk Queries - 2026-09-05.txt:139) and `eval dn = "uid=" . uid . ",ou=" . ou . ",ou=sors,dc=weill,dc=cornell,dc=edu"` (line 607). plan_deletions() computes `existing - live` where `existing` is the old-shaped DB dn set and `live` is the real entry DN set. The SOR reconstruction interpolates the *ou attribute value*, not the RDN, so any case or spelling difference makes the two shapes permanently unequal -- PORT_PLAN.md lists the affiliates branch as `ou=nyp affiliates,...` (lowercase) while the `ou` attribute plausibly reads `NYP Affiliates`. The author's own declared divergence adds that the reconstruction assumes every SOR branch is exactly one level under ou=sors, so any deeper entry already carries a wrong dn in the DB. Concrete failure: on the first live run every mismatched row is classified `gone`. If mismatches are under MAX_DELETE_FRACTION (2%) they are deleted (or soft-delete flagged) while the upsert simultaneously inserts a duplicate row under the real DN -- one live person, one tombstoned row and one new row. If mismatches exceed 2% the run raises SystemExit every night and the table silently stops being refreshed.

**Fix.** Before any live run, dump both key spaces and compare: `SELECT dn FROM _person_canonical` / `_person_sor_record` against the entry_dn set from one --dry-run, and report the exact-match rate per type. If it is not 100%, run a one-time UPDATE rewriting the stored dn to the real entry DN (matched on weillCornellEduCWID + uid, or CWID + SORID for SOR) before the first write. Regardless, force the first live run to --no-delete and gate DELETE_MODE on a measured 100% key overlap, not on the 2% ceiling -- the ceiling is sized to catch a bad feed, not a key-space change.

### [data-loss] ed_people_canonical(): `mail`, `street`, `telephoneNumber`, `weillCornellEduProviderID`, `labeledURIpops`/`labeledURIvivo`/`labeledURIonlinedirectory`. ed_sors_sor_record(): `mail`, `street`, `telephoneNumber`, `weillCornellEduStatus`, `weillCornellEduDegree`, `personalTitle`, `company` (`row.get("o;company")`). Premise stated in mv()'s docstring, buildIdentityAuthority.py:186-195.

**Problem.** The rule the slice is built on -- that the 39 `nomv` lines "declare exactly which attributes the original author knew were multi-valued" and that anything not on that list is safe for row.get() -- is wrong. `nomv` does not decide whether a set reaches the column, only the separator: it flattens a multivalue joined by newline, which is precisely why every `nomv` in the file is immediately followed by `rex mode=sed "s/\n/|/g"`. An attribute that is never nomv'd still reaches the lookup as a newline-joined multivalue and is pushed by dbxoutput as that string. For the SOR search this is not an inference about outputlookup semantics at all: `stats list(*) as * by dn` (Splunk Queries - 2026-09-05.txt:609) explicitly converts EVERY field to a multivalue immediately before `table` and `outputlookup`, so every SOR column in the DB today holds the full joined set wherever ED returned more than one value. Concrete failure: a person with mail = [jdoe@med.cornell.edu, jd2001@med.cornell.edu] has both in `_person_canonical.mail` today and gets only the first after the port; a SOR record with two weillCornellEduDegree values or two street lines loses the second. Same class as the bug that emptied the 15 person-type flags: one value into a column whose consumers expect the set, no row-count change to expose it.

**Fix.** Do not decide this from the SPL text. Run one LDAP pass over both branches recording, per attribute, max(len(row.all(attr))) across all entries, and log it; route every attribute whose max exceeds 1 through mv(), not just the nomv'd ones. Cross-check against the current DB with one query per table -- e.g. `SELECT COUNT(*) FROM _person_sor_record WHERE mail LIKE '%\n%' OR street LIKE '%\n%' OR weillCornellEduDegree LIKE '%\n%'` -- and if that count is non-zero, mv() is mandatory for those columns and the separator change (newline to pipe) needs declaring as its own divergence.

### [correctness] ed_people_canonical() and ed_sors_sor_record() docstrings, the dropped `where ... len(uid) < 20` / `len(uid) > 20`; SPL at Splunk Queries - 2026-09-05.txt:180, 189 and 611

### [correctness] ed_sors_sor_record() -> weillCornellEduStartDate / weillCornellEduEndDate / weillCornellEduDOB, read through _Row.get() rather than _ts()

**Problem.** _ts()'s own docstring identifies the hazard -- "_Row.get() normalises that to ISO-8601 WITH the offset ('...+00:00'), which is not the shape the column holds" -- and then routes only createTimestamp, modifyTimestamp and weillCornellEduHireDate through _ts(). weillCornellEduStartDate, weillCornellEduEndDate and weillCornellEduDOB are date-typed and go through _Row.get(). That ldap3 returns datetime for these specific attributes is established, not assumed: buildIdentity.py:1232 documents it and buildIdentity.py:601/790 depend on _flatten()'s isoformat() so that `[:4]` yields the year. Concrete failure: _person_sor_record.weillCornellEduStartDate receives `2019-07-01T00:00:00+00:00` while createTimestamp in the same row receives `2019-07-01 00:00:00`. If the column is typed DATE/DATETIME the insert is rejected or silently truncated; if VARCHAR, every downstream strptime / LEFT(col,10) / string comparison written against the Splunk-era shape breaks -- and the SOR search never sliced these fields, so the Splunk-era shape is whatever ldapfilter rendered, not this one.

**Fix.** Route every GeneralizedTime-syntax attribute through _ts() (or an explicit date-only variant for DOB), and confirm the target column types with one query -- `SELECT column_name, data_type FROM information_schema.columns WHERE table_name IN ('_person_sor_record','_person_canonical') AND column_name LIKE '%date%'` -- plus one sample of the existing values, so the port writes the shape already in the column rather than a third shape.

### [correctness] MIN_ROWS["sor_record"] = 20000, /Users/paulalbert/worktrees/reciterdb-ia/update/buildIdentityAuthority.py:127

**Problem.** sor_record carries the same floor as canonical although the two populations differ by a large multiple: canonical is one row per person (~33,388 per the identity port's own build log), while sor_record is one row per SOR record and every person has at least one, most several. ## Slice: roles-org (NEEDS_FIXES)

### [data-loss] slice ed_organization(), the "telephoneNumber" and "labeledURI" emit lines

**Problem.** Both are read with row.get(), which _Row flattens to the FIRST value only. Both are multi-valued by definition (RFC 4519 telephoneNumber, RFC 2079 labeledURI carry no SINGLE-VALUE) and neither is nomv'd in the SPL, so today they reach the lookup as Splunk mv fields carrying every value. This is the same class of bug the module header says emptied 15 person-type flags on the sibling port: no row-count change, so a row-count diff cannot catch it. It is also internally inconsistent -- the function's own comment four lines above states the policy ("cn, uid, seeAlso and o are multi-valued in ED but the SPL only nomv's some of its multi-values ... Joining them keeps every value, which is the point of mv()") and then abandons it for these two.

**Fix.** Use mv(row, "telephoneNumber") and mv(row, "labeledURI"). The change is free even if ED turns out to hold one value per org unit: "|".join(["x"]) == "x", so mv() and get() are byte-identical on single-valued data. Concrete failure without it: an org unit with a main line and a fax, or with both a department site and a directory URL, silently loses the second value in _organization.telephoneNumber / .labeledURI on every run.

## Slice: contact (NEEDS_FIXES)

### [data-loss] ed_phones_contact(), `"telephoneNumber": r.get("telephoneNumber") or r.get("mobile")`

**Problem.** This is the priority-1 pattern, reached via `or` instead of a bare get(). The function's own docstring asserts that a single ED entry carries both types — "LDAP returns an entry from BOTH arms of the SPL's two-branch search when it carries a desk number and a mobile" — which is precisely why weillCornellEduType is read with mv(). But the declared divergence justifies the entry_dn key with the opposite claim: "the desk entry and the mobile entry are different LDAP entries with different DNs". Both cannot be true. If the docstring's premise holds, entry_dn does NOT split them (it is one entry, one DN), and the `or` writes the desk number while silently discarding the mobile — one row, one column, no row-count change, so the row-count diff the author promises ("expect _contact_phone to gain rows") cannot detect it. Secondarily, telephoneNumber is multi-valued in LDAP (RFC 4519), so get() takes only the first of several desk numbers even when the premise does not hold. The SPL is no defence here: its two branches produced two rows that then collided on one _key, so both implementations lose the number — the port just claims to have fixed it and has not.

**Fix.** First measure the premise: run `(&(objectClass=*)(telephoneNumber=*)(mobile=*))` and `(&(weillCornellEduType=telephoneNumber)(weillCornellEduType=mobile))` against ed-phones and report the counts. If either is non-zero, stop merging the two attributes into one column — emit `mv(r, "telephoneNumber")` and `mv(r, "mobile")` into separate columns, or pipe-join them (`"|".join(r.all("telephoneNumber") + r.all("mobile"))`) so the column matches the joined-set shape the other nomv'd columns already use. Either way, correct the docstring so it states one premise, not two contradictory ones.

### [data-loss] All four sources — the `{r.entry_dn: {...}}` key — plus plan_deletions() consuming db_dns read from `_contact_email.dn` / `_contact_phone.dn` / `_contact_location.dn` / `_location.dn`

## Slice: dbside (NEEDS_FIXES)

### [data-loss] db_dns() SELECT + _merge_sql() ON clause + main() ordering (slice); vs. "Splunk Queries - 2026-09-05.txt" lines 132, 228, 296, 331, 520, 605, 675-679

**Problem.** The whole db side assumes the `dn` already stored in the IA tables is the same string ldap3 returns as `row.entry_dn`. It is not. Every SPL builder writes a RECONSTRUCTED dn: `"uid=" . uid . ",ou=emails,ou=contacts,dc=weill,..."` (line 228), `"uid=" . uid . ",ou=telephoneNumbers,ou=contacts,..."` (line 520), `"cn=" . cn . "," . seeAlso` / `",ou=departments,ou=Groups,..."` (lines 675-679). The module's own docstring concedes the Organization one "may have been writing wrong DNs for years," and the port's guessed BASE_DN entries contradict the SPL outright (port: `ou=emails,dc=weill,...`; SPL: `ou=emails,ou=contacts,dc=weill,...`; port: `ou=phones,...`; SPL: `ou=telephoneNumbers,ou=contacts,...`). Nothing in db_dns(), plan_deletions() or _merge_sql() reconciles the two forms. Confirmed: plan_deletions({'organization': {real_entry_dn: {}}}, {'organization': {spl_reconstructed_dn}}) -> "ABORT: 1 of 1 organization rows (100.0%) would be removed". Because main() calls plan_deletions() BEFORE upsert(), the first live run writes nothing at all, on every run, forever. And the flag an operator will reach for first, --no-delete, removes exactly that guard: plan={} and upsert() proceeds with `ON tgt.[dn] = src.[dn]` never matching, so `WHEN NOT MATCHED THEN INSERT` fires for every row and each affected table gets a full parallel copy under the new DN form. **Fix.** Prove the DN forms agree before any live write, and make the check independent of --no-delete. In db_dns(), after reading each table, compute the overlap against the built live set and abort if |live & existing| / |existing| is below ~0.9, with the message naming both a sample live DN and a sample DB DN (DNs are not on the sensitive-field list; mail/mobile/postalCode are). Run that check even under --no-delete, since --no-delete is the path that silently duplicates. If the forms genuinely differ, migrate the `dn` column (or add a normalized join key) before enabling either upsert or deletion.

### [data-loss] db_dns(): `SELECT [dn] FROM [table] WHERE [dn] IS NOT NULL`

**Problem.** The read does not exclude rows already soft-deleted by a previous run, so a flagged row stays in `existing` forever while being permanently absent from `live`. `gone = existing - live` is therefore CUMULATIVE, and MAX_DELETE_FRACTION (0.02) stops being a per-run ceiling and becomes a lifetime budget. Simulated on a 30,000-row `_contact_email` with 0.4% ED churn per run: run 2 = 0.80%, run 4 = 1.60%, run 6 = 2.40% -> plan_deletions raises SystemExit. Since main() runs plan_deletions() before upsert(), that abort stops the entire job -- the upsert included -- on run 6 and on every run after it. The handoff notes there is no staleness alert on this lane, so a job that has stopped writing raises nothing.

**Fix.** Exclude already-flagged rows from the reconcile read: `SELECT [dn] FROM [t] WHERE [dn] IS NOT NULL AND ([deleted] IS NULL OR [deleted] = 0)` (guarded on the column existing, same INFORMATION_SCHEMA check _delete_marker already does). Alternatively compute the ceiling against newly-gone DNs only. Either way MAX_DELETE_FRACTION must measure one run's churn, not the table's history.

### [data-loss] _columns_for() / _merge_sql() SET clause vs. _flag_sql()

**Problem.** DELETE_FLAG_COLUMN is written by _flag_sql() but is never in the MERGE's SET list, because _columns_for() only ever sees ED-sourced column names. Verified: _merge_sql('_contact_email', ['mail','ou'], 1) produces SET targets ['tgt.[mail]', 'tgt.[ou]'] only. So a soft-deleted DN can never be un-flagged. Concrete: an ED read blip drops 0.5% of email entries while the source still clears its MIN_ROWS floor (10000); plan_deletions sees 0.5% < 2% and flags them; next run they are back in ED, the MERGE happily updates mail/ou for those exact rows, and `deleted` stays set. Every consumer filtering on the flag loses those people permanently, with no row-count change on either side to catch it -- the same silent shape as the person-type bug the module was written to avoid.

**Fix.** Add an unconditional clear of the flag for matched rows: append `tgt.[deleted] = NULL` (or `= 0`) to the MERGE SET clause whenever the column exists -- presence in ED this run is exactly the evidence that the row is not deleted. Deliberately NOT COALESCE'd; this is the one column where a NULL from the source must win. Add the corresponding demo() assertion.

### [correctness] plan_deletions() set difference vs. _merge_sql() `ON tgt.[dn] = src.[dn]`

**Problem.** The two halves of the run disagree on string equality. Python's `existing - live` is case- and whitespace-sensitive; SQL Server's default collation (SQL_Latin1_General_CP1_CI_AS) is case- and trailing-space-insensitive. A DN that differs only in case matches in SQL and does not match in Python. Verified: with 200 live DNs and one DB row stored as `UID=7,ou=people,...` instead of `uid=7,...`, plan_deletions returns ['UID=7,ou=people,dc=weill,dc=cornell,dc=edu'] (0.50%, under the ceiling, so no abort). In the same run the MERGE's ON clause matches that row case-insensitively and UPDATEs it, and then apply_deletions() flags it deleted. One run both refreshes and soft-deletes the same live person. This is a distinct mechanism from the DN-form finding above and survives its fix.

**Fix.** Normalize both sides of the comparison to a single canonical key -- e.g. build `{dn.strip().casefold(): dn}` in db_dns() and key `built` the same way -- and do the set difference on the normalized keys while carrying the original DN string through to the SQL. Assert it in demo() with a case-only-divergent pair.

### [correctness] db_conn(): `database=os.environ.get("IA_DB_NAME", "IdentityAuthority")` and `IA_DB_ENV = ("IA_DB_URL", "IA_DB_USERNAME", "IA_DB_PASSWORD")`

**Problem.** IA_DB_NAME is named in the abort message but is not in IA_DB_ENV, so it is never required -- and `_mssql_target()` (buildIdentity.py:324) discards everything after the first `;`, which is precisely where a JDBC URL carries `databaseName=`. Verified: _mssql_target('jdbc:sqlserver://ia-prod.med.cornell.edu:1433;databaseName=IdentityAuthorityPrd') -> ('ia-prod.med.cornell.edu', 1433); the database name the operator supplied is thrown away and the hardcoded guess 'IdentityAuthority' is used instead. The abort message explicitly instructs the operator to build IA_DB_URL "from Splunk's Identity_Authority DB Connect connection" -- i.e. to paste exactly such a JDBC URL. If a database literally named IdentityAuthority exists on that server (a restore, a dev copy), the run connects to it, db_dns() logs plausible counts, and a full snapshot is MERGEd into the wrong database while every log line reports success. The comment above IA_DB_ENV says writing IA rows into the wrong server "would be far worse than refusing to start", but nothing actually verifies the target.

**Fix.** Add IA_DB_NAME to IA_DB_ENV so it is a required secret, or parse `databaseName=` out of IA_DB_URL when present and refuse when the two disagree. Then log `SELECT DB_NAME(), @@SERVERNAME, SUSER_SNAME()` once at the top of db_dns() so the target appears in the run log.

### [correctness] db_dns() -- counts are logged but never asserted; plan_deletions() `if not existing: continue`

**Problem.** Hazard #3 on the DB side is unguarded. Sources have MIN_ROWS; the DB read has no floor at all. db_dns() logs `rows=%d distinct=%d` and moves on whatever the number is, and plan_deletions() treats a zero-row DB side as benign ("db side empty, nothing to reconcile"). A wholly failed or empty read is therefore indistinguishable from a fresh table, and combined with the finding above it is the only thing that could have caught a connection pointed at an empty copy of the schema. It also means a half-empty read (say `_person_canonical` returning 4,000 of 33,000 rows) passes silently: it suppresses real deletions and hides that the read was truncated.

**Fix.** Give db_dns() a per-type floor -- reuse MIN_ROWS, or a DB_MIN_ROWS keyed the same way -- and raise SystemExit naming the table and both counts when a read falls under it. Treat `existing` empty as an abort unless an explicit IA_ALLOW_EMPTY_TABLE=<type> opt-in is set for a genuinely new table.

### [correctness] _merge_params(): `[_null_if_blank(row.get(c)) for c in columns]`

**Problem.** This is the one call in the slice that does the exact thing the module's header warns about at lines 67-73 ("a plain .get() silently emptied 15 person-type flags on the sibling port and was invisible until a production diff"), and it has no guard. It is safe only while every source returns plain dicts. _Row is a dict subclass, so one source returning `{dn: _Row(...)}` -- or building its row dict by copying a _Row -- passes every check here and every assertion in demo(). Verified against the real _Row: a plain dict carrying 'academic|academic-faculty|affiliate' binds that whole string, while the identical _Row binds 'academic'. _columns_for() even accepts the lowercased _Row keys without complaint, and SQL Server identifiers are case-insensitive so the column names still resolve. Result: one value written into a column whose consumers expect the pipe-joined set, no row-count change, invisible to a row-count diff.

**Fix.** Refuse ambiguous row objects at the boundary. In upsert(), before building params: `bad = [dn for dn, r in items if type(r) is not dict]` and SystemExit naming the source and type if non-empty. Or bind with `row[c] if c in row else None` on a plain-dict-only contract. Add a demo() assertion that a _Row-valued built dict aborts.

### [correctness] main() (new): `unresolved = UNRESOLVED_ALIASES & {fn.type_name for fn in SOURCES.values()}`

**Problem.** This intersects LDAP alias names with type names, which are disjoint by construction, so the warning can never fire. Verified: UNRESOLVED_ALIASES = {'ed','ed-emails','ed-groups','ed-locations','ed-phones'}; type names = {'canonical','email','location','location_master','organization','phone','sor_record','sor_role_record'}; intersection = set(). The run therefore proceeds against five guessed base DNs with no warning whatsoever -- and the SPL's own dn reconstructions show at least three of those guesses are wrong (`ou=emails,ou=contacts` not `ou=emails`; `ou=telephoneNumbers,ou=contacts` not `ou=phones`; `ed-locations` is used for two different subtrees, `ou=locations,ou=contacts` at line 296 and `ou=locations,ou=Groups` at line 331). The declared divergence says the new main() "reproduces the --demo/--spike paths verbatim", which is true -- but it reproduces a broken guard verbatim, and this block is the last chance to fix it.

**Fix.** Record the alias on the source (`fn.alias = alias` in the @source decorator, or a module-level SOURCE_ALIASES map) and intersect on that. Better: make it an abort rather than a warning for a live (non --dry-run) run, since a guessed base DN that binds to the wrong subtree produces wrong DNs, which is the failure in the first finding.

### [correctness] apply_deletions(): `marker = _delete_marker(cur, table) if DELETE_MODE == "flag" else None` sits below the `if dry_run: ... continue` branch

**Problem.** _delete_marker() is the only thing that verifies DELETE_FLAG_COLUMN exists, and it is unreachable under --dry-run. So a green --dry-run in flag mode proves nothing about the column whose name the code itself calls a guess. The live run then aborts inside apply_deletions() -- after upsert() has already committed -- with a message about a column nobody verified. This is hazard #6 from the identity port ("three green dry runs passed while the SQL was malformed") reproduced in the very function whose docstring cites it as the reason the delete branch refuses in dry-run too.

**Fix.** Move the INFORMATION_SCHEMA check ahead of the dry_run branch and run it in both modes: open a read-only connection under --dry-run (db_dns() already requires one in that path, so no new credential requirement) and call _delete_marker() for every table in the plan before logging the statement. Report the resolved marker value and its declared type in the dry-run log.

### [correctness] _merge_sql(): `row_ph` CASTs all of `cols`, key included; plus `WITH (HOLDLOCK)` inside upsert()'s single all-tables transaction

**Problem.** The CAST is justified for value columns (a bare NULL in a VALUES constructor really does type as int), but the key column can never be NULL -- it is the dict key from `built` -- so the rationale does not apply to it, and casting it costs the join. `ON tgt.[dn] = CAST(... AS NVARCHAR(MAX))` compares against a LOB-typed expression; if the stored `dn` is `varchar`, nvarchar's higher precedence forces CONVERT_IMPLICIT on the column and the index seek is lost outright. That matters because _batch_size() is small: verified 43 rows/batch at 45 columns, so `_person_sor_record` at ~40k rows is ~931 separate MERGE statements, `_person_canonical` ~688, `_person_sor_role_record` ~704. Each of those potentially scans its table, and all of them run under HOLDLOCK (serializable range locks) inside one transaction that spans all eight tables for the entire run. Concrete failure: the 600s `timeout` in db_conn() expires mid-run, or the IA database's readers block for the full duration of the job. (MERGE_MAX_ROWS = 1000 is also dead -- `2000 // (cols + 1)` is always the binding limit.)

**Fix.** Do not CAST the key: build the row constructor as `%s` for column 0 and `CAST(%s AS NVARCHAR(MAX))` for the rest, so the ON clause stays SARGable, and assert the shape in demo(). Separately, scope the transaction per table (commit after each type, log which types committed) so a failure on table eight does not hold locks over the whole database while tables one to seven wait -- the all-or-nothing property is worth stating explicitly as per-table if that is what it becomes.

### [style] upsert() and apply_deletions(): `except Exception:` around bodies that `raise SystemExit(...)`

**Problem.** SystemExit derives from BaseException, not Exception (verified: issubclass(SystemExit, Exception) is False), so the unmapped-type abort and _delete_marker()'s missing-column abort skip the rollback branch entirely. The transaction is still discarded when conn.close() runs in the finally, so no data is lost -- but the log line 'upsert rolled back -- no table was modified' never prints on those paths, and that line is what an operator reads to decide whether anything landed.

**Fix.** Use `except BaseException:` for the rollback-and-log block (re-raising unchanged), or add an explicit `except SystemExit:` arm alongside it.
